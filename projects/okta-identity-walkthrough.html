Identity and access / Lab walkthrough

Set up my Okta
SSO and lifecycle lab.

Use a free Okta developer account to centralize sign-in with SAML 2.0, control access with groups, and automate joiner, mover, and leaver changes.

OktaSAML 2.0SCIM 2.0Google WorkspaceOkta System Log

Why I built this lab

Single sign-on and lifecycle management are core IAM skills. I wanted hands-on proof that I understand how companies centralize sign-in and make sure access is granted, changed, and removed through groups instead of one person at a time.

Make it your own. This is how I did it, not the only way. Feel free to adjust the lab to your liking: change the names, tools, or scope, or take it further. What matters is that you understand what you built and why.

Before you start

  • A free Okta developer account.
  • A test application that supports SAML 2.0 and, for provisioning, SCIM 2.0.
  • Optional: a Google Workspace test environment to practice SSO into a real service.

What you’ll learn

  • Identity Provider (IdP) vs. Service Provider (SP) roles
  • SAML 2.0 federation and SSO configuration
  • Group-based access and least privilege
  • SCIM provisioning and Joiner/Mover/Leaver workflows
  • Monitoring identity events in the Okta System Log

How it fits together

  1. Okta tenantUsers and groups by job function.
  2. SAML app integrationOkta signs users in to the app.
  3. Group-based accessApps assigned to groups, not people.
  4. SCIM provisioningAccounts created, updated, removed automatically.
  5. System LogAudit sign-ins and lifecycle events.

Step by step

  1. Set up your Okta tenant

    Create a free Okta developer tenant and configure the organization settings, branding, and domain.

  2. Create users and groups

    Add test users and create groups mapped to job functions. You’ll assign apps to these groups instead of to individual people.

  3. Create a SAML 2.0 app integration

    • Go to Applications → Create App Integration → SAML 2.0.
    • Enter the service provider settings: Single sign-on URL (ACS URL), Audience URI (Entity ID), and Name ID format.
    • Add attribute statements to map the user attributes the app needs.
    • Finish, then use Okta’s IdP metadata (or SSO URL and certificate) to configure the app’s side.
    • Sign in through Okta and confirm it works. A browser SAML tracer extension lets you see the assertion and verify the claims.

  4. Optional: SSO into Google Workspace

    Configure Google Workspace as a service provider with Okta as the IdP: set the sign-in URL and Entity ID, and upload the Okta certificate. Enable SSO for test users and confirm sign-in redirects through Okta. Then disable a user in Okta and confirm they can no longer get into Google Workspace.

  5. Assign access by group

    Assign each application to the groups that need it. Sign in as an unassigned user and confirm access is denied. That’s least privilege at the group level.

  6. Turn on SCIM provisioning

    On an app that supports SCIM 2.0, enable provisioning and map attributes between Okta and the app so accounts are created, updated, and deactivated automatically.

  7. Test Joiner, Mover, and Leaver

    • Joiner: create a user and add them to a group. Confirm they’re provisioned to the group’s apps.
    • Mover: move the user to another group. Confirm their app access changes.
    • Leaver: deactivate the user in Okta. Confirm app access is revoked and the account is deprovisioned.

  8. Review the Okta System Log

    Open Reports → System Log to review provisioning events and sign-ins. Filters help you find what matters, for example failed attempts:

    text
    outcome.result eq "FAILURE"

    Export the logs to practice getting identity events into a SIEM.

Check your work

  • Signing in through Okta gets you into the app.
  • Unassigned users are denied access.
  • Joiner, mover, and leaver changes show up in the app automatically.
  • The System Log shows the sign-in and provisioning events.

Clean up

Deactivate and delete your test users and remove test app integrations when you’re done.

Interview ready

Be ready to explain

  • The difference between the IdP and the SP, and what’s inside a SAML assertion.
  • Why group-based assignment scales least privilege.
  • How SCIM prevents orphaned accounts when someone leaves.
  • How you tested each Joiner, Mover, and Leaver scenario.
  • Why the Okta System Log matters for identity threat detection.

Know your work front to back and you’ll be ready when someone says “walk me through it.”
